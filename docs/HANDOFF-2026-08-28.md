## O que é o projeto

PWA de pesquisa de satisfação de pacientes do **Instituto São Vicente (ISV)**,
rodando em tablets fixos (quiosque) nas unidades de saúde. Paciente responde
um formulário multi-step (NPS + estrelas de Recepção/Limpeza/Atendimento/
Espera + comentário opcional); os dados vão para uma planilha Google Sheets
via Google Apps Script. Uma equipe interna acessa um dashboard (senha) para
ver métricas, gráficos e comentários.

- **Stack:** HTML/CSS/JS puro (sem framework/bundler), PWA com Service
  Worker, backend em Google Apps Script + Google Sheets, gráficos com
  Chart.js no dashboard, deploy estático via GitHub Pages.
- **Organização:** Instituto São Vicente (ISV), responsável de TI: Henrique
  (henrique.krvalho@gmail.com).
- **Repositório:** branch `master`, deploy automático via GitHub Pages.

3. **v1.1.11** — troca do transporte de envio do formulário do paciente de

   `postDataComIframe` foi mantido como **fallback automático** caso o

4. **v1.1.12** — numa revisão geral pedida "a frio" (sem diff associado,

   fila offline (`trySyncQueue()` em `pesquisa.html`) sobrescrevia a fila
   inteira do `localStorage` usando um snapshot tirado no início da
   sincronização — se um paciente terminasse o formulário durante essa
   janela, a resposta dele podia ser perdida silenciosamente. Corrigido
   pra reler a fila do zero ao final e remover só os itens confirmados
   como enviados.
5. **docs** — `CLAUDE.md` atualizado com a seção "Modo de operação"
   documentando a virada pra produção plena/manutenção (ver acima).

## Arquitetura / arquivos-chave

```
projeto-pesquisa-satisfacao/
├── CLAUDE.md                ← contexto mestre, leia primeiro
├── CHANGELOG.md             ← histórico versão a versão
├── index.html                ← tela inicial (links pra pesquisa/dashboard)
├── pesquisa.html             ← formulário do paciente (CRÍTICO, tablets)
├── dashboard.html            ← painel administrativo (senha protegida)
├── sw.js                     ← Service Worker (bump em toda mudança JS/CSS)
├── manifest.json / manifest-dashboard.json
├── appscript/codigo.js       ← backend Apps Script (doGet/doPost)
├── appscript/deploy.ps1      ← deploy do backend via clasp
└── docs/                     ← este handoff + docs de referência
```

Fluxo: tablet → `pesquisa.html` → `fetch()` (fallback iframe) → Apps Script
`doPost` → grava aba **Respostas** → `dashboard.html` lê via `doGet` com
token.

## Segurança (mitigação parcial, documentada e aceita)

- Endpoints de leitura (`?action=dados`/`dadosAntigos`) exigem um token
  compartilhado (`DADOS_TOKEN`, precisa ser idêntico em
  `appscript/codigo.js` e `dashboard.html`). Antes disso eram 100%
  públicos/anônimos.
- **Não é controle de acesso robusto** — o token é visível em texto puro
  pra quem ler o código-fonte publicado no GitHub Pages. Decisão
  consciente, documentada no `CLAUDE.md`.
- Restrição por domínio Google Workspace foi **avaliada e descartada
  definitivamente**: o ISV só tem uma conta real no domínio, todo o resto
  da equipe usa e-mail pessoal. Só reconsiderar se o ISV distribuir contas
  Workspace de verdade pra toda a equipe (decisão organizacional deles).
- Sessão do dashboard (`localStorage`, 30 dias, renovando a cada acesso)
  **não é revogada** trocando a senha na planilha — só bloqueia login
  novo. Enhancement possível, não implementado (não pedido ainda).

## Débito técnico conhecido e aceito (não é "esquecido", é decisão registrada)

- Fallback iframe ainda existe em `postDataFetch` (pesquisa.html) — de
  propósito, como rede de segurança caso `fetch` falhe num device
  específico.
- `entrada.id = Date.now()` no cliente (sem componente aleatório) — seguro
  hoje (kiosque, um paciente por vez), mas seria um problema mais real com
  múltiplos tablets por unidade. Achado do revisor em 28/08, classificado
  como "aviso", não corrigido ainda por não ser urgente.
- `getDados`/`getDadosAntigos` no backend leem a aba inteira a cada
  chamada (sem paginação) — funciona bem no volume atual, é o item #1 da
  lista de "o que quebra primeiro" na escala da Fase 2 (ver abaixo).

## Fase 2 — expansão pra outros equipamentos de saúde (AGORA ATIVA)

Contexto: ISV atende **13 municípios**, com UBS/PSF/hospitais/UPAs — alguns
municípios têm dezenas de postos. O piloto atual (4 unidades, 1 município)
é uma fração pequena do volume-alvo final.

**Auditoria de escalabilidade já feita** (2026-08-20, revisor + cotas
oficiais do Google) — ordem real de ruptura ao crescer:

1. 🔴 Dashboard sem paginação (`getDados`/`getDadosAntigos`) — degrada
   sozinho com o tempo, sem precisar de rajada de tráfego.
2. 🔴 ~~Perda silenciosa via transporte iframe~~ — **substancialmente
   mitigado em v1.1.11/v1.1.12** (fetch como transporte principal + fix da
   fila offline). Risco residual baixo, não mais item crítico isolado.
3. 🟡 Lock único de escrita (`LockService` em `doPost`) — tráfego orgânico
   tem folga ~10x, mas rajadas correlacionadas (~20-25 unidades
   reconectando juntas após queda de rede compartilhada) já estouram hoje.
   Cota real do Google: ~30 execuções simultâneas por usuário — teto da
   plataforma, não nosso.
4. 💡 Limite de células do Google Sheets (~10M células) — 1-7 anos de
   folga dependendo da adoção.
5. 💡 `<select>` de Unidade fica ruim de navegar acima de ~50-80 opções.
6. 💡 Rate limit global (1000/60s) — nunca é o gargalo isolado.

**Conclusão prática já registrada:** dá pra crescer até **~20-40 unidades
sem mexer em nada**, só monitorando. Acima disso, os itens 1 (paginação) e
3 (modelo de concorrência do backend) deixam de ser teóricos.

**Ação imediata ao retomar esta sessão:** perguntar/confirmar com o
usuário **quantos equipamentos de saúde entram nesta leva do rollout**.
Comparar com a margem de ~20-40 acima:
- Se estiver dentro da margem → seguir com o rollout normalmente
  (replicar o padrão de configuração via aba **Equipamentos**), sem
  mudança de arquitetura.
- Se estourar a margem → antes de continuar adicionando unidade, priorizar
  paginação em `getDados`/`getDadosAntigos` e revisitar o modelo de lock
  do `doPost` — tratar como projeto técnico separado, não como parte do
  rollout de campo.

**Passos operacionais do rollout (por unidade nova), reaproveitando o
padrão já usado em Caucaia:**
1. Cadastrar a unidade na aba **Equipamentos** da planilha (município +
   nome da unidade).
2. Se for um município novo (fora de Caucaia): pedir a arte oficial do
   logo ao marketing, adicionar em `assets/municipios/`, mapear em
   `MUNICIPIO_LOGOS` (dentro de `pesquisa.html`), incluir o arquivo no
   array `URLS` do `sw.js` pra cache offline, e bumpar a versão do SW.
   Município sem logo mapeado não quebra — só não mostra logo
   (fallback gracioso), mas não é o ideal pra apresentação oficial.
3. Configurar o tablet físico com o overlay protegido por senha
   (município + unidade).
4. Confirmar que a unidade aparece nos filtros do dashboard (é dinâmico,
   lê da aba Equipamentos — deve funcionar sem mudança de código).
